## Project notes

- **Dependencies: keep `pnpm audit` at zero, and keep tooling out of `dependencies`.** The 2026-11 dependency pass cut 78 advisories to 0 — three of them critical in `next` — by moving `shadcn` (a CLI that only ever runs against `components.json`, never imported by app code) from `dependencies` to `devDependencies`, which alone removed most of the transitive tree (`hono`, `@hono/node-server`, `qs`, `body-parser`, `minimatch`, `systeminformation`, `@modelcontextprotocol/sdk`) from the deployed artifact. Anything that is a code generator or a test runner belongs in `devDependencies`. Transitive fixes that cannot come from a direct bump live in `pnpm.overrides` in `package.json`, keyed by range (`"hono@<4.13.16": "4.13.16"`) so a future major is not dragged along. One exception worth remembering: **`vite` is only a peer of `vitest`/`@vitejs/plugin-react`, and pnpm does not rewrite auto-installed peers**, so `pnpm.overrides` has no effect on it — pin it as a direct `devDependency` instead.
- Two separate journeys, never merged: **GitHub import** (`/new/github` → `lib/projects/create-project.ts`) brings a repository in to build; **connected business** (`/new/existing` → `lib/existing-business/*`) reads a live website and connects an app that keeps running outside Atai. The existing-business path never reads a repository.
- Onboarding asks the fork before anything else: step 2 of the mission (`/dashboard?mission=1`) is `path` — build something new, bring a codebase, or connect a business that already runs (`ONBOARDING_PATHS` in `lib/onboarding/profile.ts`, rendered by `components/onboarding/path-step.tsx`). `destinationForPath()` in `lib/onboarding/state.ts` decides where it leads: `connect` → `/new/existing`, `import` → `/new/github`, `build` → the vision beat. Never infer the journey from what the founder types; ask.
- The business profile (`/project/[id]/business`) is a three-step stepper — `lib/existing-business/steps.ts` decides order and completion (assessment → domain proof → connection), `components/existing-business/business-profile.tsx` renders only the active step. Keep it one step at a time: a wall of every section at once is what made the page unreadable.
- Connected-business pages share one layout language, matching `/new/existing`: a mono eyebrow (`font-mono text-[11px] uppercase tracking-[0.18em]`), an `h1` at `text-2xl sm:text-3xl`, a `max-w-2xl` support line, then a `lg:grid-cols-[minmax(0,1fr)_300px]` split — the step card on the left, a sticky aside holding the progress rail, a per-step "why this matters", and "what Atai never does". Inside a step card, use numbered sub-steps and `border-t` sections; do not nest `Card` in `Card`.
- A finished step announces itself: `sonner` toast plus a dismissible success strip, and the view advances to the next step. Nothing is marked done on optimism — `businessSteps` reads the same view the server builds.
- Run control is two-phase: `startIntakeRun` awaits only the decision (access, eligibility, rate limit, single-writer claim) so `POST /api/projects/[id]/intake` can answer `started: true|false` or a refusal with a message; `runBusinessIntake` keeps the awaiting form for tests and cron. A fire-and-forget POST cannot tell the founder that a retry was refused, which is exactly how an inert "Try again" button happened.
- After a start the profile polls on its own (`watching`) until the assessment has a verdict — the view returned by a start is the pre-run one, so polling only while `overall` is pending leaves the page frozen on a failed stage.
- Assessment parsing is per-field and tolerant (`normalizeResponse` in `lib/existing-business/assessment.ts`): renamed keys, an omitted section or one weak finding must not fail the whole run. Only a payload with no findings and no priorities is rejected, and a rejected reply gets exactly one repair attempt inside the same charge and time budget. Parse failures are logged with `reason` and `model` — that log line is the answer to "why did the assessment fail?".
- The handshake happens outside the page, so the connection step never depends on a reload: `ConnectionCard` (`components/existing-business/connection-card.tsx`) carries `Check now`, which re-reads `/api/projects/[id]/intake` through the profile's `refresh` and says what it saw ("no authenticated call has reached Atai yet" vs recorded). The status itself is derived on read — `recordConnectionSeen` (runtime health) is what writes `firstSeenAt` — so nothing extra has to be persisted for the check to be honest.
- Connection truth lives in `lib/connected-business/` (`businessConnectionStatus` needs both a verified domain and a first authenticated call). Access helpers: `userHasBuiltBusiness` (Atai-built app) vs `userHasRealBusiness` (built **or** connected) in `lib/dashboard/business-access.ts`; nav items declare `requires: "built" | "business"`.
- Connecting a business is priced as a journey, not as whatever pipeline mode the project happens to carry: `existingBusiness.readCost` + `existingBusiness.assessmentCost` in `lib/billing/runtime-config.ts` (admin billing → "Connecting a Business"), charged internally per stage by `chargeBusinessReadCredits` and the assessment's own `consumeCredits` call. `businessJourneyCost()` prices only the stages still unpaid, and both `startIntakeRun` and `GET /api/billing/business-connect` quote it before any work starts.
- Refusals for credits go through `failInsufficientCredits` (402 + `{ required, available, …meta }`) and reach the founder as `CreditsShortfallDialog` — price, balance, exact gap, current step, top-up link — never as a bare red line. Extend the dialog's copy via `describeShortfall` so it stays testable without a DOM (the suite runs in `node`, not jsdom; UI assertions use `renderToStaticMarkup`).
- Phase A2 payment attribution: `lib/billing/subscription-payment-grants.ts` links each subscription payment to the exact ledger grants it funded (`creditsGranted`, `grantLedgerEntryIds`, `grantBucketIds`). `refund.succeeded` reverses only those buckets (`reverseSubscriptionCredits`), never permanent credits or today's catalog; missing or ambiguous grant history stays `reversalStatus: "unresolved"` for review. A grant with only a ledger reference and no `grantBucketIds` is refused (`grant_bucket_unresolved`) rather than guessed. Historical payments reconcile with `scripts/reconcile-subscription-payments.ts` (`dry-run` first, then `apply`); it links only one unambiguous grant and marks everything else `grantStatus: "needs_review"`.
- `reverseCredits` returns `requestedAmount`, `availableAmount`, `expiredAmount`, `consumedAmount`, `previouslyReversedAmount`, `shortfall`, `shortfallReason`, `missingBucketIds`, and the exact `bucketDeductions`. Refunds record that shortfall on both the refund row and the original payment, so "grant was consumed/expired/already reversed" is distinguishable without guessing. The ledger debit and its metadata are written after the flat and bucket updates in the same transaction; a missed bucket write throws and rolls the whole reversal back.
- Phase A4 subscription grants: `grantSubscriptionCredits` reads `subscriptionCredits` and `credits` inside the same transaction that increments them, pushes the bucket and writes the ledger; its ledger snapshot uses the applied `balanceBefore`/`balanceAfter`, plus `totalBalanceBefore`/`totalBalanceAfter`. No balance read or lazy expiry runs before the grant transaction. Duplicate period grants are blocked by the ledger idempotency key and the in-transaction re-check. Renewal expiry passes `expiresAtOrBefore: now` so an annual-sweep bucket for the new period cannot be removed by old-period cleanup; `subscription.expired` still removes the whole subscription. Regression coverage lives in `lib/billing/subscription-payment-grants.test.ts` (Phase A4) and `lib/billing/credit-service.grant.test.ts`.
- Phase A5 infrastructure lifecycle: infrastructure plans are fixed-duration, credit-funded entitlements — there is **no Dodo recurring billing** for them and `autoRenew` stays false. `activatePlan` stores `purchasedTerms` (plan, limits, price, duration), charges the existing ledger with a purchase idempotency key, and applies the Totalum cap; an explicit `{ renewal: true }` extends from the current paid-through date, while an ordinary purchase starts a new period. A short `infrastructure.lifecycleLock` serializes purchase/renewal with `handleExpiration`. `GET /api/admin/infrastructure/expire-sweep` (`0 7 * * *`) downgrades expired paid plans to Testing and applies the real Totalum cap; a cap failure leaves the record `expired` + `syncStatus: "failed"` for retry, and route-level `infrastructureDenial` blocks build/followup/deploy/database/server operations as soon as the paid-through date passes. Historical records with no trustworthy expiry are marked `needsReview`, never auto-expired or repriced. Tests: `lib/infrastructure/lifecycle.test.ts` and the deploy route's expired-infrastructure case.
- Refund concurrency is guarded in three places: the ledger idempotency key, `creditReversalKeys` on the user (one balance decrement per reversal), and `refundIds` on the original payment (one `$inc` per refund). The refund row and the original payment's progress commit in one transaction, and a full refund that lands mid-sweep stops the annual scheduler before the next month.
- Phase A3 credit integrity: `reverseCredits` is the one authoritative reversal path. It debits the exact grant buckets, the flat aggregates and the ledger in a single transaction, and accepts an existing `session`; `reverseSubscriptionCredits` is now a thin wrapper. A grant-scoped reversal (`bucketIds` / `subscriptionId`) never falls back to the customer's total balance, so permanent credits and other subscriptions are untouched. The refund handler runs the reversal, refund row and original-payment progress in that same transaction, and caps cumulative refunds atomically with `refundedAmountMinor: { $lte: originalAmount - refundAmount }` (plus `$exists: false` for the first refund), so two different concurrent refund ids cannot over-refund.
- Cancellation and plan changes never touch credit records: cancellation only changes subscription status, and `subscription.plan_changed` only re-pins terms. Existing buckets keep their original expiry and amounts. Expiry remains scoped to one subscription (`expireSubscriptionCredits`) or to overdue buckets (`expireOverdueBuckets`); promotional grants are permanent credits and are never debited by subscription expiry or refund.
- Legacy bucket/aggregate drift is found by `inspectUserCreditIntegrity` / `auditCreditIntegrity` and repaired by `repairCreditBalance` (`lib/billing/credit-reconciliation.ts`), which aligns `subscriptionCredits`/`credits` to the itemised buckets and writes a `credit_reconciliation` ledger entry with the actor and reason. It never creates or edits a bucket. Run `scripts/reconcile-credit-balances.ts dry-run` first; `apply` requires `--actor` and `--reason`. A legacy account with no buckets is left alone apart from its `credits` mirror.
- **One business belongs to exactly one Atai account.** A business is its live hostname; the claim is the `business_domains` record itself — there is no second registry. `canonicalBusinessHost()` (`lib/domain/host.ts`) strips a safe leading `www.` for the uniqueness key only; the exact hostname stays the verification target, so `www.example.com` and `example.com` are one business, `shop.example.com` is another, and `www.co.uk` is left alone. `canonicalHostname` carries a unique partial index (`business_domains_canonical_active_unique`, excluding released records and `aliasOf` rows) — the database, not a check-then-insert, settles races.
- The claim is taken **before** a project row or a credit: `createUserProject` calls `reserveBusinessClaim` first (reservation only, no token) and reuses the reserved project id. Outcomes: `reserved` → create; `reuse` (same account, another business) → return that project with `reused: true`; `refused` → 409 `BUSINESS_ALREADY_CONNECTED`. Never disclose the holder — `BUSINESS_ALREADY_CONNECTED_MESSAGE` in `lib/domain/claim-copy.ts` (client-safe, imported by the wizard) is the only sentence a founder sees.
- Apex + www inside one project is one business: the second exact host is stored as an `aliasOf` record so it can still be verified. Unverified reservations expire after `CLAIM_RESERVATION_TTL_MS` (72h) — `expireStaleClaims` releases them so the unique index frees up; verified claims never expire. Deleting a project releases every claim in the same transaction (`MongoStore.deleteProject`), and `releaseDomain` refreshes the cached connection status.
- Intake is claim-gated: `ensureBusinessClaim` runs before the credit check and the crawl, and a claim refused at domain registration stops the run before the assessment. The outcome is persisted on `project.intake.claim` (`state: "yours" | "held_by_other"`) and surfaced as `view.claim`; the profile then shows `ClaimHeld` instead of verification controls. Preflight for the wizard is `GET /api/business/availability?url=` (`claimStateFor`) — a failed preflight must never block creation, which re-checks.
- **A dialog that has not answered yet is loading, not empty.** `readingPreviewState()` (`lib/existing-business/reading-preview-state.ts`) decides the body of `reading-preview-dialog.tsx`: no payload and no error is `loading` (skeleton + "fetching the copy"), only a payload with `reading: null` is `empty`. Rendering the "no copy was kept" copy while the request was in flight is what made a slow read look like a broken one — the founder closed the dialog and only saw the content on a second click. Never derive "there is nothing" from "we have not been told yet"; keep a previous payload visible with a "checking for a newer read" hint rather than blanking it.
- **A read is judged by what it shows.** `lib/existing-business/website-facts.ts` builds both the founder's copy (`IntakeWebsiteReading`, rendered by `components/existing-business/reading-preview-dialog.tsx`) and the co-founder's evidence block (`buildWebsiteDigest`). The digest must carry real page text (`Text:` per page, bounded by `DIGEST_PAGE_TEXT_CHARS` inside a single `DIGEST_TEXT_BUDGET`), not only titles, headings and navigation — headings describe a site without saying anything about the business. Crawl markdown is cleaned by `toReadableText()` (link targets and image syntax stripped) before either consumer sees it, and `crawlWebsite({ mainContentOnly: true })` drops nav/footer for the intake read only; the SEO auditor keeps the full document.
- **The first read runs on the founder's engine, and a failure names that engine.** `runAssessment` (`lib/existing-business/intake.ts`) resolves `resolveCofounderModel(project.userId)` — the same tier that answers the co-founder chat, fail-soft to the shared `MODEL` — and passes it as `AssessmentInput.engine`. A failed call stores `engine` and `errorReason` (`timeout`, `model_unavailable`, `rate_limited`, `provider_error`, `rejected`, `format`, `unknown`) on `intake.assessment`, so `EngineTroublePanel` (`components/existing-business/engine-trouble-panel.tsx`) can say which engine failed, in the founder's words, and offer a way out. A raw `nvidia/…:free after 91s (timeout)` line as the whole explanation is a dead end: it names a model the founder never chose and suggests nothing to do. The panel offers `Fix the issue` (an in-place tier picker backed by `GET /api/settings/ai-model`, which returns the live catalog plus the engine that would answer) and keeps `Try again` for founders who would rather not switch. `/settings/ai?next=<path>` shows the way back, so a detour never loses the saved read; once the stored `engine` differs from the current one the panel stops blaming it and asks for one more try. `COFOUNDER_MODEL_TIER` still pins the engine deployment-wide; `OPENROUTER_MODEL` no longer decides this read.
- **The read costs the write plus the founder's engine, quoted exactly as charged.** `existingBusiness.assessmentCost` is the flat price of the write; the tier's admin-set `creditsPerMessage` is added on top, because that is what the turn costs us. `businessJourneyCost` and `GET /api/billing/business-connect` both resolve the surcharge with `assessmentEngineSurcharge()` — the same resolver the run uses — and return `{ assessmentCost, engineCost, engineName, required }`, so the number in the wizard, the profile line and `CreditsShortfallDialog` is the number `generateBusinessAssessment` debits. A quote that ignores the engine is a founder quoted 60 and charged 65. Once the read is paid for, the surcharge disappears with the rest of the price — a finished stage is never charged twice.
- **A retry is a new charge, not a replay.** The assessment debit is keyed on `collab_…_{amount}_{attemptId}`, where `attemptId` is the run's `attemptedAt`, and the refund is keyed on the same string. Keying only on user + project + amount made the ledger treat the retry of a *refunded* attempt as an already-processed event (`consumeCredits` dedupes on the key), so every retry after a failure ran for free. The id is per attempt, not per call, so a duplicated call inside one attempt still debits once.
- **Reads follow the address the site actually serves; claims never do.** `crawlWebsite` reports `WebsiteEvidence.finalUrl` from the provider's post-redirect URL, and page discovery/filtering runs against that host — filtering against the typed URL is what collapsed a preview-URL read to one page. `collectWebsiteFacts` records `redirectedFrom`, and both the digest and the dialog state the two addresses. `registerIntakeDomain` claims only the address the founder typed, plus a redirect target that is the *same site* (same registrable domain, never across a shared host like `*.vercel.app`): a redirect is not proof of ownership, and auto-claiming it would squat a host nobody verified.
- **The method toggle is a view choice, and the check follows it.** Both artifacts come from the same token, so `DomainVerification` keeps the choice in local state (`methodFor(domain, choice)`) and switches on the first click — no PATCH, no disabled button, no waiting. The choice rides along on `POST /verify` (`{ method }`), and `verifyDomainOwnership({ method })` fetches that artifact and persists `method` on success. The old `set_method` round-trip made a one-click switch feel broken: the control stayed disabled for the length of a request, and two controls (the registration radios and the card toggle) competed for one value. The radios now only appear before a challenge exists. A check that silently used the stored method while the founder looked at the other instructions is a false failure; never reintroduce that.
- **A verification file name is short, hashed and fixed at creation.** `fileNameForToken()` returns `atai-verify-<12 base64url of sha256(token)>.txt` — short enough to find in a host's file manager, and it reveals nothing about the token. `doc.fileName` is stored, and `verifyDomainOwnership` fetches exactly that (falling back to the derived name only for rows that lack one), so an old challenge keeps the long name it was created with and a founder mid-challenge never has to re-upload. A 404 on the file is nearly always the wrong folder, so the failure names the exact URL and says where "site root" actually is per host (`public/` on Vercel/Next.js — the repository root is not published; `public_html` on WordPress). Never answer a 404 with "token did not match": that sends a founder hunting for a file that is simply not being served. Every long token in this step (the file name, the URL the check opens) is one unbreakable string, so it wraps with `break-all` inside a `min-w-0` child and the dialog keeps `overflow-x-hidden` with a pinned footer — a card or dialog that scrolls sideways on a phone is a broken step, not a cosmetic bug.
- **Verification never accepts a cross-site hop.** `verifyDomainOwnership` passes `allowHostnameChange: false, allowSameSiteRedirects: true` to `safeFetchDocument` for both methods, so apex↔www and sibling subdomains still verify while a hop to another registrable domain fails `REDIRECT_HOST`. Without that, a host that redirects to a site you control could be "verified" by a tag that was never on it. `isSameSiteHost()` (`lib/domain/host.ts`) is the one rule for "same site" — apex↔www and sibling subdomains, never across a shared host — shared by the crawl, the redirect policy and the read-match; `isSharedHostingHost()` stays the shared truth for shared platforms.
- **The domain step verifies the address the co-founder read.** `DomainVerification` shows `view.website.url` (via `hostnameOfUrl`) as a one-click "Verify this address"; free text sits behind "A different address?" and says plainly that the first read does not describe it. Never make the typed address the default target again — a founder who edits the URL there silently verifies a site the assessment never saw, and every sentence the co-founder writes about "your site" becomes false. `readHostnameOf(project)` (`lib/existing-business/view.ts`) is the one source for that address; `registerDomain({ readHostname })` stores `matchesRead` on the record, `toDomainView(doc, { readHostname })` recomputes it, and the co-founder tool ships it to the model so it can say the two are different sites. A claim on another site is still a real proof of ownership — label it, never hide it and never block it.
- **A proof settles one address, not the addresses beside it.** `unresolvedDomainClaims()` (`lib/existing-business/steps.ts`) is the one rule — anything neither `verified` nor `revoked`, whose reservation is still live, needs a decision — and the domain step is `done` only when that list is empty. A live reservation blocks every other account from that hostname, so leaving one behind locks a site nobody can connect; proving one address used to close the step and abandon the rest invisibly. A reservation that has run out is inert (the same rule as `claimIsActive` in `lib/domain/service.ts`) and stops holding the step open. `DomainVerification` lists every waiting address with `Prove this one` (the guide for that claim, or `New challenge` when the token is stale) and `Remove`, plus `Remove all N`, and the footer says why the next step is still closed.
- **Nothing is released without the warning dialog.** `DomainReleaseDialog` (`components/existing-business/domain-claim-dialogs.tsx`) is the only way a claim goes away — no inline confirm, no bulk action without a list of the exact hostnames — because releasing frees the site for any other Atai account and takes a proved address (and the connection that counts on it) back to unverified. When a proof lands while others wait, `UnresolvedDomainsDialog` asks immediately rather than letting the founder discover it later.
- **A refused redirect names the address that answered.** `DomainFetchError.hostname` (set only when the target is a public destination) rides through `verifyDomainOwnership` into `failure.hostname` and `doc.lastFailure.hostname`, so the card offers "Verify shop.example.net instead" instead of a dead end. Never put a private or internal address in that field.
- Verify with `npx tsc --noEmit`, `npx vitest run` and `npm run lint` (flat config `eslint.config.mjs`: typescript-eslint recommended + the two classic react-hooks rules + Next's recommended rules; the React Compiler rules in react-hooks v7 are deliberately not enabled). Lint must report zero errors; the remaining warnings are pre-existing `no-explicit-any`/`no-unused-vars` debt.
- A verified claim is evidence that has to keep being true. `lib/domain/recheck.ts` re-checks verified, unreleased domains oldest-first on a daily cron (`GET /api/admin/domains/recheck`, `20 3 * * *`), at most once per `RECHECK_MIN_INTERVAL_MS` (20h), 25 per run with a 240s budget. It calls the same `verifyDomainOwnership({ reverification: true, internal: true })` the founder does — `internal` skips the per-user/per-domain attempt limits, because our own sweep is not a person hammering a check. A failure raises `needsAttention`; only `REVERIFICATION_FAILURE_GRACE` consecutive failures expire the claim, and a sweep never releases a claim on its own.
- The 72h reservation is silent unless we speak: `lib/domain/claim-notices.ts` (`GET /api/admin/domains/claim-notices`, `40 4 * * *`) emails one reminder inside the last 48h of an unverified claim and one notice if it actually expired. The reminder window is deliberately wider than the daily interval so every 72h claim is caught at least once. `expiredUnverified` marks releases that came from the window, so nobody is emailed about a release they performed themselves; `claimReminderSentAt` / `claimExpiryNoticeSentAt` dedupe, and a failed send leaves the flag unset so the next run retries. The deadline is visible in the domain card (`claimExpiresAt` on `DomainView`, `relativeDeadline()` in `lib/client/format.ts`).
- Support release is the audited exception, not a code change: `lib/domain/claims-admin.ts` backs both `/admin/domains/claims` and `scripts/release-business-claim.ts`, and both write `released by support (<actor>): <reason>` into the record's history. A reason is mandatory. It never deletes anything — the record is marked `revoked` + `releasedAt`, so the unique index frees the hostname and the audit trail survives.
- The verification token is encrypted at rest (`lib/domain/token-cipher.ts`, AES-256-GCM, key derived from `AUTH_SECRET` or an explicit 32-byte `DOMAIN_TOKEN_KEY`). Storage holds ciphertext; service callers work with plaintext — `getOwnedDomain` / `listProjectDomains` / `toDomainView` decrypt, `registerDomain` / `ensureChallenge` / `regenerateChallenge` encrypt on write. `decryptDomainToken` passes through legacy plaintext values, so old rows keep working until they expire or are regenerated. Never log or return `token` outside the owner-gated view.
- The connect journey is instrumented separately from the build funnel: `lib/analytics/connect-funnel.ts` emits `connect_started` → `connect_submitted` → `connect_read_completed` → `connect_verified` → `connect_completed`, plus `connect_claim_blocked` (with `state: held_by_other | held_by_same_account`) which is the signal that separates a blocked squatter from a blocked real owner. Flat primitives only; never send the hostname, URL, project id or email — a random `flow_id` joins the steps.
- Root of the repo is source and config only: `README.md`, `CHANGELOG.md`, `AGENTS.md`, `CLAUDE.md`, configs. Implementation reports go in `docs/history/`, audits in `docs/audits/`; build artifacts (`*.tsbuildinfo`, `tsc-*.txt`, `test-out.txt`, probe scripts) are ignored and must not be committed.
- `pnpm` is the only package manager (`packageManager: pnpm@10.6.0`, `pnpm-lock.yaml`). Do not reintroduce `package-lock.json` — two lockfiles can disagree and CI installs with `pnpm install --frozen-lockfile`. CI (`.github/workflows/ci.yml`) runs typecheck → lint → tests → build, so lint warnings that become errors block a merge.
- Plan enforcement is centralized in `lib/billing/entitlements/require.ts`: a production build/follow-up checks `buildProduction` + `provisionDatabase` + `useSpecialistTeam` in one fresh decision, deploy checks `connectSubdomain` only when the project has no published URL, and custom domains spend a registration only when none exists. Existing domains/subdomains stay manageable after a downgrade.
- `GET /api/projects/[id]` returns `access` (`ProjectAccessView` from `lib/billing/entitlements/presentation.ts`) so the UI can disable actions and show the server's reason. It is presentation only; every mutating route re-checks. Terminated paid subscriptions fall back to Explorer; only a legacy free account that never subscribed keeps grandfathered production capability.
- Capacity is reserved, not just read: `lib/billing/entitlements/reservations.ts` serializes the read-check-reserve section with a short DB lock and writes a TTL hold (`billing_resource_holds`) before the provider runs. Custom-domain/subdomain holds count toward the cap; storage holds count bytes until the asset row exists. Routes call `reserveCustomDomainSlot` / `reserveSubdomainSlot` / `reserveProjectStorage` instead of authorize-then-write — two requests can otherwise both see the last slot. Provider failure releases the hold; a provider success followed by a failed project write keeps it so a retry cannot hand the slot to another request. Expired holds are never counted and TTL indexes clean them up. Both the REST deploy route and the shared `startProjectDeploy` (Co-founder tool + pipeline recovery) use the same sequence, and `state: "deploying"` counts as a subdomain slot. `ENTITLEMENT_ENFORCEMENT_ENABLED=false` fails plan-capability guards and the access view open, but keeps the pre-existing infrastructure storage byte quota, credit checks and provider checks running — it disables the entitlement layer, not every guard.
- An uninitialized project has no free pass: `getProjectStorageUsage` falls back to the Testing 50MB cap when no infrastructure record exists, so uploads before the first build cannot bypass the quota. `lib/billing/entitlements/hold-maintenance.ts` and the daily `GET|POST /api/admin/billing/entitlements/resource-holds` sweep (`50 3 * * *`) delete expired locks/holds, release holds for deleted projects or already-persisted domains/subdomains, and leave live storage holds until TTL. Use `?dryRun=true` before manual cleanup.
- Commercial catalog (A7.0–A7.5): the database catalog is authoritative only when **both** `CATALOG_SOURCE=db` and `CATALOG_DB_PUBLIC_READS=enabled`; either flag off keeps the code catalog in charge. Admin flow is product draft → publish candidate → preview (`GET /api/admin/billing/catalog/publications/preview`) → explicit activation (`POST …/publications/[version]/activate` with the previewed checksum). Activation validates with the same `resolvePublicationCatalog` used by customer reads, supersedes the previous active publication in one transaction, and refuses Dodo-id, price, credit or entitlement drift. Checkout fails closed (`CATALOG_UNAVAILABLE` 503) when a database catalog is selected but invalid; webhooks resolve the active version through `lib/billing/catalog/runtime.ts`, fall back to code only on a catalog read failure, and pin the database price/credits/entitlement snapshot. Existing subscriptions always keep their `purchasedTerms`; activation never flips the read gates.
- `next.config.mjs` sets the security headers (`X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, COOP, HSTS) and a **report-only** CSP — report-only on purpose, because App Router ships inline bootstrap scripts and an enforced `script-src` needs nonces through middleware. `images.unoptimized` is deliberate (ImageKit already optimizes; Vercel's optimizer would bill a second pass).
- **Money moves in one place only:** `lib/billing/credit-service.ts` (grant / consume / reverse / expire, all idempotency-keyed and transactional) and `lib/billing/dodo-event-processing.ts` (verified webhooks → effects). Never write a balance field directly; never grant from a route. The 2026-11-21 audit (`docs/audits/atai-monetization-engine-audit-2026-11-21.md`) records the invariants and the open gaps — read it before touching pricing, plans or refunds.
- Plan prices and monthly credit grants are **code constants** (`lib/billing/entitlements/catalog.ts`: `PLAN_PRICING`, `PROVISIONAL_MONTHLY_CREDITS`, `PLAN_BASE`), not admin data. `PATCH /api/admin/billing/configuration` cannot reach them, and `setPlanCreditAllocation` mentioned in `catalog.ts` does not exist. A renewal resolves its grant from *today's* constant (`dodo-event-processing.ts` `plan?.mirrorCredits`), ignoring the `mirrorCredits` stored on `subscription_records` — so editing a grant silently re-prices every existing subscriber. Pin the subscription before changing a number.
- A subscription payment row carries **no `creditsGranted`** (credits belong to `subscription.*` events), so the refund handler reverses `0` for subscription refunds. Packs reverse correctly. Any change to refund handling must cover both paths.
- `subscription_records.pricingVersion` / `entitlementVersion` point at `plan_catalog_versions` / `entitlement_versions`, which exist only in `docs/ATAI_PHASE2_ARCHITECTURE_DESIGN.md`. Entitlement snapshots are written by the migration script, not by checkout activation.
- Entitlement enforcement is wired for create / fork / build / deploy / launch only. `registerCustomDomain`, `connectSubdomain`, `provisionDatabase`, `useStorage`, `useSpecialistTeam`, `useCompetitionIntel` and `useAgent` are defined and unit-tested but have **no call site** — wire the route, don't assume the check happens. `applyWebhookDowngrade` (read-only marking for over-limit businesses) is likewise unused.
- Infrastructure plans (`lib/infrastructure/plans.ts`, priced in Atai credits) are charged once at activation; `handleExpiration` and `checkStorageLimit` have no callers and no cron, so "credits/month" never recurs and storage limits are unenforced. `vercel.json` runs four crons (expiry sweep, annual sweep, domain recheck, claim notices) — webhook recovery is manual only.
- Dodo product ids come from `DODO_COMMERCIAL_PRODUCT_<PLAN>[_ANNUAL]`; with no env var, checkout creates the product on demand with the price in its name (so a price change never reuses a stale product). Admin-created products in `/admin/dodo-products` are **not persisted** anywhere — checkout only finds them by exact name.
- **Connected Business (ADR-8) is a second product surface, not a project mode.** A business owns applications, memberships and connected services. `lib/business/` holds the domain: `access.ts` is the only authorisation entry point, `permissions.ts` the role matrix (owner = all; admin = all except `money.manage`), `members.ts`/`applications.ts`/`service.ts` the operations. `lib/types/business.ts` holds the documents. The import boundary is enforced by `lib/business/independence.test.ts`: `lib/business` may not import `lib/projects`, `lib/marketing`, `lib/cofounder`, `lib/runtime`, `app/project` or `lib/types/project`, and those may not import it. The project↔business bridge lives in `lib/connected-business/`.
- **Membership is the authorisation source of truth; `businesses.ownerId` is never consulted.** Every business operation takes an explicit `Actor` and calls `requireBusinessAccess` before its first write — enforced structurally by `lib/business/authorization-coverage.test.ts`, which walks nested modules and detects arrow exports. Adding an operation means gating it or adding a justified entry to that file's `EXEMPT` map. Non-member and unknown business are 404; a member without the permission is 403; a member outside an application's scope is 404 for that application.
- **A member can only grant scope they already hold.** `addMember` and `reactivateMember` compare the requested scope with the actor's own; a scoped admin cannot hand out another application or the whole business. Creating an application requires an unscoped `apps.manage`, because a new application belongs to nobody's scope yet. One active owner per business is a partial unique index (`business_members_one_owner`), and ownership cannot be granted, removed or moved through member management.
- **Business creation is transactional and stamped.** `createBusiness` inserts the business and seats the owner in one `session.withTransaction`; every read inside it must carry `{ session }` or it cannot see the uncommitted insert. The fake collections in `lib/business/testing/fake-collections.ts` enforce that rule and fail loudly — they also model partial unique indexes, including on `updateOne` (a restore is where a partial index actually bites), and `$ne: null` means "exists and is not null" there exactly as in MongoDB. They are a model, not a database: they do not prove driver retry, write conflicts or index builds, so a replica-set integration test is still required before migration writes production data.
- **The workspace rollout is controlled from `/admin/connected-business`, not from Vercel.** `lib/business/flags.ts` reads one document (`business_rollout`, id `connected-business`); the `CONNECTED_WORKSPACE_V2` / `CONNECTED_WORKSPACE_COHORT` env vars are only the fallback while no admin has saved a setting, and the page shows which one is deciding. Mode is `off | internal | all`, unrecognised means off, and a failed read falls back to env then to off — a broken read must never open a surface. `GET|PATCH|DELETE /api/admin/connected-business` is `requireAdmin`-gated; PATCH takes a closed enum (an admin typo is rejected, an env typo falls back to off). A partial edit must not disturb the other half: the write seeds `mode`/`cohort` via `$setOnInsert` from the effective value, because an upsert writes only the fields it is given and a cohort-only edit on a fresh database would otherwise have created a document with no mode, switching the surface off. Outside the rollout both the pages (`app/business`, `app/business/[businessId]`) and the API (`app/api/businesses/**`) answer 404, not 403. Route handlers only authenticate and validate; all decisions are made by the services. **The surface needs a way in.** `GET /api/business/access` returns `{ enabled, reason }` for the caller (never 404 — it is not a gate). `shellNavigation()` in `components/dashboard/dashboard-shell.tsx` is **static**: one entry per destination, `All businesses` → `/projects`, and no `Connected business` entry, because connected businesses are listed in that one portfolio and a second link would lead to the same page under a different name. `components/dashboard/dashboard-shell-nav.test.ts` fails if a `/project/…` or `/business` href appears there. Any `tour:` id used in the shell must be registered in `lib/tour/targets.ts`; `lib/tour/targets.test.ts` fails otherwise. The single `Current business` card stays: it is capped at one and answers "where am I", which a list of destinations cannot.
- **`requireWorkspace` is async and rate-limited.** It reads the rollout from the database, so every call site must `await` it (a Promise is always truthy, which TypeScript cannot catch — `lib/business/gate-await.test.ts` guards it structurally). It also charges a per-user bucket: `business.read` 240/min for GETs, `business.write` 60/min for writes; the flag check runs first so a user outside the cohort always gets a plain 404 and the limiter cannot be used to probe access.
- **Migration is preflight → dry-run → apply → verify, and reversible by run id.** `npm run migrate:businesses:preflight` is the readiness gate (no-go on a non-replica-set or a unique index that cannot be created, warnings for ownerless projects, unusable addresses, already-owned claims and dangling claims); `npm run migrate:businesses -- dry-run|apply --run-id=<id> [--project=<id>] [--user=<id>]`; `npm run migrate:businesses:verify` exits non-zero on problems; `npm run migrate:businesses:rollback -- dry-run|apply --run-id=<id>` deletes only rows stamped with that run. A migrated business carries `legacyProjectId`, which makes apply idempotent. Never run `apply` without a preflight and a dry run. The procedure, what each output means, and the rehearsal evidence are in `docs/runbooks/connected-business-migration.md`.
- **The migration scripts cannot run under bare `tsx` without `tsconfig.scripts.json`.** Every migration module starts with `import "server-only"`, which Next aliases at build time but a standalone Node process cannot resolve; `scripts/shims/server-only.ts` plus the `paths` mapping in `tsconfig.scripts.json` fix that. `tsx` is not a dependency, so the npm scripts call `npx --yes tsx` (an offline machine needs `tsx` installed and the flag kept). One-shot scripts must also call `closeDatabase()` from `lib/db/shutdown.ts` in a `finally`: an open client keeps the event loop alive so the report prints and the process hangs, and closing before the lazy index build settles surfaces as an unhandled pool error after the report.
- **A legacy project with no `userId` is skipped, not adopted.** The owner member is the only row that grants access, so migrating an ownerless project would create a business nobody can reach. Preflight reports these; the migration records `no owner on the legacy project` and moves on.
- **`apply` requires an explicit `--run-id`** (`lib/connected-business/cli.ts`); a dry run may generate one. The run id is the only handle rollback has, so a generated apply id is a handle nobody wrote down. `--project` and `--user` narrow together, not one instead of the other.
- **Rollback is a guarded recovery operation, not a delete button.** `rollbackMigration` preflights every business the run created and blocks — writing nothing — when any of them was renamed (`updatedAt` past the stamp), gained a member or application with no stamp for this run, or had a stamped child removed or archived. `--allow-in-use` is the separately authorised path: it prints the impact, deletes only stamped rows, and reports the founder rows it orphans. `updatedAt` is a signal, not proof, which is why the child checks exist. Domain claims are detached only when they carry this run's stamp and still point at one of its businesses.
- **`/projects` is the one portfolio, and it holds both kinds of business.** A connected business (ADR-8) is not a project, but it is a business a founder runs, so it is listed beside the projects with the same card, row, search, tabs and sort — only the destination (`/business/<id>`), the label (`Connected business`) and the status badge differ. The pure view model is `app/projects/portfolio.ts` (`filterPortfolio`, `countTabs`, `itemHref`, `matchesTab`), covered by `portfolio.test.ts` and `workspace-render.test.ts`; the server page only fetches — and fetches connected businesses **only when the rollout is open for the account**, so a closed surface never leaks names into the portfolio. A connected business has no build state, so its status answers the tab question: `draft` → in progress, `active` → live, `suspended` → needs attention, `archived` → archived (which is what finally gave that tab content). Destructive actions stay where they belong: projects keep the delete dialog, connected businesses open their workspace, where archive is reversible and confirmed.
- **Archiving is reversible.** `restoreBusiness` runs through the same gate with `allowArchived`, which is the only write permitted on an archived business. It restores the status recorded in `archivedFrom` at archive time and records `restoredBy`/`restoredAt`. Do not add another `allowArchived` caller: every other write must stay blocked while archived. Applications follow the same rule: `archiveApplication` is a soft delete and `restoreApplication` (`POST /api/businesses/:id/applications/:appId/restore`) is the only caller of `allowArchivedApplication`, because `assertApplicationInBusiness` hides archived rows from every other operation. The origin index is partial on `archivedAt: null`, so a restore can collide with an address claimed while the row was archived — that surfaces as `APPLICATION_ALREADY_EXISTS`, never a silent duplicate. Archiving from the UI is confirmed first, and archived applications are listed under `Archived` so the action is visibly reversible.
- **Permanent deletion is owner-only, re-authenticated, and cascades in one order.** `DELETE /api/businesses/:id` archives; `POST /api/businesses/:id/delete` (`deleteConnectedBusiness` in `lib/connected-business/deletion.ts`) removes permanently. The founder types their account email and, for a password account, their current password (social accounts confirm with email only) — the same re-auth rule as account deletion. `deleteBusiness` (owner only, `allowArchived`) releases every claim stamped with the business id and removes memberships and applications in one transaction; the orchestrator first deletes the anchor project through `store.deleteProject`, which revokes keys, cascades project data and releases project-stamped claims. Project first, then business, and every step is idempotent, so a retry is safe and the hostname is free for another account. Billing, refund and audit records are deliberately retained.
- **A migrated business is `active`; a founder-created one is `draft`.** The two creation paths differ on purpose (A′.5 F-11): one already exists in the world, the other is an empty shell. `verify` mirrors the unique index exactly — duplicate origin within one business is a problem, the same origin across two businesses is a warning — so its exit code can gate a deploy.
- `hostVerified` on an application is set by the verification workflow only. It is not accepted from request input, and `createApplication` writes `false`.
- **A partial index predicate cannot use `$exists: false`.** MongoDB rejects it as `$not: {field: {$exists: true}}`, so the index never builds — and because `runEnsureIndexes` batches, one bad predicate silently skips every index after it. Use `field: null` to mean "missing or null". This was a live defect until A′.4 (three indexes, including `connected_applications_origin_unique`, had never existed in production). Real-database tests: `scripts/test-replica-set.sh start`, then `MONGODB_REPLICA_URI=... pnpm test:integration`; they skip loudly without the URI and never count as passing. Vitest runs test files in parallel, so each integration file must own its database — `test/integration/connected-business-flow.mongo.test.ts` derives `<db>_flow` from the URI because it wipes the business collections between cases and would otherwise race the migration test.
- **Referral attribution is carried by an edge cookie, not by sessionStorage.** `proxy.ts` writes `Atai_referral` from any `?ref=` (first touch wins, 30 days) and every auth path reads it: `captureReferral` for email, Google, and GitHub. The old client-only `referral_code` in `sessionStorage` was read during the first render, before the page effect stored it, so OAuth buttons were built without a ref and every social signup arrived unattributed. `AuthPanel` now resolves the code in an effect and passes it to the buttons; the register route falls back to the cookie. A referral is one row per referred user — never overwrite, never self-refer, never create a cycle.
- **Both sides are paid.** `captureReferral` grants the referred user `referralSignupBonus` (admin billing → rewards, default 500) with idempotency key `referral_signup_<referralId>`, and the referrer gets `referralVerificationReward` on verification plus `referralMilestoneReward` at `referralMilestoneThreshold` (`processVerificationReward` / `processMilestoneCheck`). OAuth signups arrive pre-verified, so `captureReferral` settles the referrer's verification reward immediately instead of waiting for a verify-email route that never runs. A failed bonus grant is logged, never allowed to fail signup. The referred user is emailed and sees a toast (`ReferralWelcomeToast` for OAuth via `welcome=referral&bonus=`, a `sonner` toast for password signup).
- The programme is documented publicly at `/referral-program` (`components/referral/referral-program-section.tsx` is reused on the landing page and pricing). Its numbers come from the public billing config, not literals; the terms and refund policy state that referral credits are promotional and non-refundable.
- **Customer-facing billing copy has one source:** `lib/billing/public-config.ts` (`getPublicBillingConfig`) reads rewards, build-tier costs, mirror-pipeline costs, deployment costs, visual-generation pricing and live offers from `runtime-config.ts`; `GET /api/billing/public-config` serves the same values to client components through SWR. Marketing, docs, terms, refund, register, referral and settings surfaces must read this config, never repeat a number. Server pages that call it export `dynamic = "force-dynamic"` so an admin change is not frozen into a static build. The welcome grant in `lib/auth/users.ts` and the referral rewards in `lib/referrals/referrals.ts` also resolve from `getRewardSettings()` at grant time.
- **Every runtime price has an admin control, and the control is reachable.** `/admin/billing/configuration` is the pricing control centre: it edits collaboration, build-tier, mirror-pipeline, existing-business, SEO-audit, deployment, visual-generation, fork, infrastructure and reward values, and links to Catalog authoring (plan/pack prices), Runtime API pricing, Offers & campaigns, Advertising packages, Dodo products and Reconciliation. The reward editor was defined but never rendered before 2026-11-22 — a card that exists only in the source is not an admin control. The page's anchor rail and the billing hub must both keep pointing at every editable surface.
- **Visual-generation charges are runtime-configurable too.** `getVisualPricing()` (`runtime-config.ts`) supplies `markup`, `creditsPerUsd`, `fallbackCredits` and `estimatedCredits` to `computeVisualCredits()` and the generate-visual route's upfront balance check. The per-model `fixedCreditCost` stays in the model catalog; the global conversion, margin and fallback are admin data, not constants.
- **Offers add credits; they never discount the catalog price.** `PromotionalOffer` (`lib/billing/offers.ts`) lives in the billing settings document and is managed at `/admin/billing/offers`. Checkout resolves the best live matching offer and stamps `offerId` + `offerBonusCredits` on the Dodo metadata, so a later edit cannot change what the customer was promised. Credit-pack bonuses are added to the permanent `credits` grant; plan bonuses are added to the first subscription grant, so they expire and refund with that grant. Public pricing shows only live offers. A missing or malformed offer row is ignored; it must never block checkout.

- **An SEO audit is a crawl, and a crawl is paid for.** `seoAudit.auditCost` in `lib/billing/runtime-config.ts` (default **100** credits, edited at `/admin/billing/configuration` → "SEO & site analysis") is the one price. `getSeoAuditCost()` in `lib/marketing/seo/credits.ts` reads it — there is no `SEO_AUDIT_CREDIT_COST` env var and no literal at a call site, so repricing never needs a deploy and can never disagree with what the panel quoted. `getSeoAuditAffordability` quotes it, `chargeSeoAuditCredits` debits it before the crawl, `runSeoAuditRequest` refunds exactly `chargedAmount` on failure (an admin repricing between charge and refund must not refund the new price), and the panel says the gap and offers a top-up instead of a disabled button. A cost of 0 is the only way the ledger is skipped. `app/api/businesses/[businessId]/seo-audit/route.test.ts` is the end-to-end money path: proved address only, 100 debited before the crawl, 402 with `{ required, available }` and no crawl when short, exact refund on failure, and a repricing that changes the debit with no code change.
- **The operate surface is one design language, in one module.** `components/connected-business/page-ui.tsx` holds `PageHero` (eyebrow → `h1` → support line → chips → actions), `SectionCard` (icon tile, title, description, action, `border-t` body), `StatTile`, `EmptyPanel` and `Chip`. Every operate page composes those instead of inventing markup, so a new page looks like the product on the first try. `components/connected-business/page-ui.test.tsx` pins the contract. The rules that keep it from breaking on a phone: the shell's nav is a horizontal scroll strip (never wrapped into three rows), long hostnames/tokens sit in a `min-w-0` child with `break-all`, and nothing sets a fixed width. **One `h1` per page** — `BusinessProfile` takes `headingLevel="h2"` on the Overview page, because the hero owns the page title there.
- **A state that has not answered is not an empty state.** The SEO panel shows a skeleton while the crawl runs and the credits-gap line when the balance is short; the score ring is drawn only when a stored score exists, so an audit without a score never looks like a perfect one.

## One business, two surfaces (Slice 1)

A connected business and an Atai-built app are both businesses, but they are managed on **different surfaces that never link to each other**. This is the product rule; everything below exists to enforce it mechanically.

- **The rule lives in one pure module: `lib/connected-business/surface.ts`.** `workspaceModeOf(project)` answers `operate` when the project carries a `businessId` or `startingPoint === "existing_business"`, otherwise `build`. `businessBase(id)` / `projectBase(id)` return a `WorkspaceBase` whose `href(page)` and `segment(target)` build every link a shared engine needs. `segment()` maps a build-only target (`source`, `database`, `deploy`, `runtime`, `collaborate`, `hosting`, …) to `/business/<id>/growth` instead of producing a dead `/project/…` link — a recommendation must never point at a screen the founder cannot open. `href("collaborate")` on the operate surface resolves to `/plan`: the growth planner *is* the conversation there. **A base that crosses into a Client Component must be data.** `BusinessProfile` is a Client Component and the operate Overview is a Server Component, so it is given `businessBaseRef(id)` — `{ mode, base, serializable: true }` — and rebuilds the link builders with `workspaceBase(ref)` inside the client bundle. Passing the `WorkspaceBase` itself throws *"Functions cannot be passed directly to Client Components"*, which in a production build reaches the browser only as "An error occurred in the Server Components render" (React #441) and a page that will not load; the `serializable` marker turns that mistake into a type error. `growth/seo` maps to `/growth` on this surface, because the audit renders there and a link to a route that does not exist is a dead end.
- **A stored row the current parser would not write must not take a page down.** `businessPriorities` (`lib/connected-business/growth.ts`) maps the stored assessment to the operate view, so it normalises the horizon instead of trusting it: a priority written before `priority` existed reads as the neutral `short_term`, not `undefined`. `priority.replace(...)` on that value used to crash the whole Growth page. Fix shapes at the adapter that reads storage, not with `?? []` scattered through the UI.
- **The isolation is tested, not remembered.** `lib/connected-business/isolation.test.ts` walks the shipped source: `app/business/**` and `components/connected-business/**` may contain no `href`/`router.push` into `/project/`; `app/project/**` may mention a `/business/` route only in a `redirect(`, never a link. `lib/connected-business/surface.test.ts` covers the pure rules. Add a new engine surface by passing a `WorkspaceBase`, never by hardcoding a path.
- **The anchor project is the adapter.** Credits (`collaborationIdempotencyKey(userId, projectId, …)`), `api_keys.projectId` and runtime auth are project-scoped. Rather than re-key all of them, a business keeps one hidden project and every shared engine is called with its id: `resolveBusinessAnchor({ businessId, actor, permission })` in `lib/connected-business/anchor.ts` is the only place that knows the link, so `lib/business` still never imports a project. Resolution order is `project.businessId` → `businesses.legacyProjectId` → `connected_applications.legacyProjectId`; more than one match is refused (`BUSINESS_NOT_MIGRATED`) rather than guessed, because linking the wrong project charges the wrong credits.
- **`ensureBusinessForProject({ projectId, userId })` is idempotent and must never block the connect flow.** It creates the business (`createBusiness`), claims the project atomically (`updateOne({ id, businessId: { $exists: false } })` — two concurrent callers cannot both win), creates the `marketing_site` application from the site address, and stamps the reserved domain claims with `businessId` (`linkClaimToBusiness`) so a business-addressed read can find its verified hostname. It is called from `create-project.ts` (fire-and-forget, logged, never thrown into the response), from `/projects` for connected projects that lack a row (capped at 5 per render), and from the stepper page. The existing connect flow in `lib/existing-business/**` and `/new/existing` is **not** modified — the business is a wrapper around it, not a replacement.
- **The gate: `businessWorkspaceAccess(userId)` in `lib/business/flags.ts`.** `isBusinessWorkspaceEnabled` still answers "is this account in the rollout cohort?" and is kept for staging. The product promise is stronger: **an active member of a business is always inside.** Only an *admin-saved* `off` (`rollout.source === "admin"`) closes the door on a member, because a broken surface must be switchable off in an incident; a deployment default is not a decision. `requireWorkspace` (API) and both business layouts use it, so a connected founder reaches `/business` immediately. An account with no business simply gets an empty list.
- **The workspace is `app/business/[businessId]/`** — `layout.tsx` (gate + `BusinessShell`), `page.tsx` (Overview = the existing stepper, rendered with `base={businessBaseRef(id)}`), `applications`, `growth`, `growth/studio`, `plan`, `money`, `settings`. `BusinessShell` is deliberately not `DashboardShell`: the operate surface has no source, database, environment, hosting or deploy groups, so it must not render the project navigation at all. Applications and Settings reuse `BusinessWorkspace` with `initialTab`/`showTabBar={false}`/`showHeader={false}` — all existing mutations (create app, archive, members, archive business) are preserved, not rewritten.
- **The build workspace is closed to an operate project** by `app/project/[projectId]/layout.tsx`, which redirects to `/business/<businessId>`. It is a layout on purpose: it covers every project *page* but not `/api/projects/**`, which the connected app's runtime and SDK still need through the anchor project. It does not redirect a project with no `businessId` yet — that is the stepper's job (`/project/<id>/business` ensures the business, then forwards), and redirecting it would loop.
- **One portfolio at `/projects`.** `app/projects/page.tsx` fetches `listBusinessesForUser` unconditionally, ensures a business for connected projects, and excludes every operate project from the build list (by `businessId`, by `legacyProjectId`, and by `startingPoint === "existing_business"`), so one business never appears twice and the build surface never lists a business. `/business` is now a redirect to `/projects`; the old index component was deleted.
- **The co-founder has an operate surface.** `POST /api/businesses/[businessId]/cofounder` calls the same `runAgentTurn` with `currentSurface: "business"`; `lib/cofounder/tool-registry.ts` filters `BUILD_ONLY_TOOLS` (`request_build`, `request_deploy`, `propose_plan_update`, `get_plan`, `create_project`, …) out of both `immediateTools(surface)` and `confirmationTools(surface)`, and `agent.ts` refuses a `prepare_request` for a tool the surface does not allow. A business turn therefore cannot propose a build, a deploy or a plan-at-build. It also keeps **its own conversation**: `lib/connected-business/cofounder.ts` only reuses a conversation whose `activeProjectId` is the business's anchor, so the build transcript is never replayed on the operate surface.
- **Growth reuses the read, not the deployment engine.** `GET`-time it reads `project.intake.website.reading` and `assessment.result.priorities`; `POST /api/businesses/[businessId]/intake` (and `GET .../intake`, `GET .../intake/reading`) runs the same `startIntakeRun(anchor, { allowReassessment })` through a business-addressed route, so the founder's browser never sees the anchor id.
- **The connection guide is the SDK onboarding, and it is a file.** `lib/connected-business/guide.ts` (`INTEGRATION_GUIDE_VERSION` 1.1) generates a brief written to be handed to a coding agent, not read by a person: `npm install @atai-group/sdk`, where the secret goes, `health.check()` as the handshake, the events to record, and the browser snippet. `trackingPlanFor(objectives)` turns `project.intake.objectives` into at most eight events (`signup` and `purchase` always; `lead_captured`, `checkout_started`, … for the goals the founder picked), so the file asks for what this business actually needs. It describes **two** keys — the runtime key (server secret) and the publishable key (ships in the page, analytics only) — and the old line "Atai has no browser-safe key type" is wrong now that publishable keys exist; a brief that says it makes an agent refuse to install the snippet. The downloadable copy carries a fresh analytics-scoped runtime key and is regenerated on each download (the previous one is revoked), so the preview uses placeholders. Settings renders it through `components/connected-business/sdk-setup-card.tsx`, whose steps mirror the file's order.
- **A component shared by both surfaces takes its links from the base.** `ConnectionCard` renders on the build surface and on the operate Overview; its "Runtime keys & usage" link was a hardcoded `/project/<id>/runtime`, which on the operate surface redirects straight back to `/business/<id>`. It now takes `runtimeLink` and `BusinessProfile` passes `{ href: routeBase.href("settings"), label: "Keys & usage" }` when the base is `operate`. A grep-based isolation test cannot see a template literal, so the guard is `business-profile.test.tsx`: rendering with an operate base must emit no `href="/project/…"`.
- **The stepper takes an `apiBase`, so no anchor id reaches the browser.** `BusinessProfile` and its three children (`DomainVerification`, `ConnectionCard`, `ReadingPreviewDialog`) default to `/api/projects/<id>` and the operate surface passes `/api/businesses/<id>`. The business routes mirror intake, reading, integration-guide and domains (`GET|POST`, `PATCH`, `POST …/verify`) with one permission each: reading/intake → `growth.read`, integration guide → `runtime.keys.manage`, domain create/change/verify → `apps.manage` (there is no `domains.manage`).
- **A business operation is authorised by membership; the records belong to the owning account.** `resolveBusinessAnchorProject({ businessId, actor, permission })` returns `{ project, ownerId }`. Authorise with `actor`, then hand `ownerId` to every service that scopes rows by user — `createApiKey`/`revokeApiKey`, `registerDomain`, `setDomainMethod`, `regenerateChallenge`, `releaseDomain`, `verifyDomainOwnership` all match on the record's `userId`, so a member passing their own id would see an empty domain list and issue keys on the wrong account. Credits are the exception: `startIntakeRun` and `chargeSeoAuditCredits` take the **acting member**, because a credit balance is personal. `app/api/businesses/[businessId]/business-routes.test.ts` pins both halves (404 non-member, 403 missing permission, who pays, who owns).
- **One address Atai may audit: `auditableSiteUrl(project)` in `lib/connected-business/site-url.ts`.** A successful deployment's `productionUrl` for a build project; the hostname the founder proved (`verifiedHostnameForBusiness`) for a connected business; `null` otherwise. Never a typed URL — that is the difference between "audit my site" and "audit someone's site". The SEO route, the growth tool and the co-founder's `run_business_seo_audit` all resolve through it, and the refusal copy follows the reason: `NOT_DEPLOYED` ("deploy first") for a project, `NOT_VERIFIED` ("prove your domain first") for a business.
- **The charged audit exists once:** `lib/marketing/seo/request.ts` (`runSeoAuditRequest`) does price → charge → crawl → refund-on-failure for both routes. Adding a third caller must call it, not copy it.
- **Exactly one SEO audit tool per surface.** `run_seo_audit` takes a `projectId` and is in `BUILD_ONLY_TOOLS`; `run_business_seo_audit` takes no id — its target is `ctx.activeBusinessId`, and the pending action stores a server-written `{ businessId }` that the approval path re-authorises (the approval route's project-ownership re-check is skipped because the parameters carry no `projectId`, which is why the business tool must re-run `resolveBusinessAnchorProject` itself). `OPERATE_ONLY_TOOLS` mirrors `BUILD_ONLY_TOOLS`, and `tool-registry.test.ts` asserts the symmetry.
- **The operate brief describes the business, not the anchor project.** `buildActiveProjectBrief(..., { operate: true })` drops `mode`'s siblings — plan health, build state, deployed URL, analytics consent — because a connected business has none of them, and `agent.ts` selects it from `currentSurface`. The anchor id still travels as `activeProjectId`/`activeBusinessId` on `ToolContext` for the tools that are project-scoped.
- **A site Atai does not host is `measurement: "none"`, never a grid of zeroes — until the founder installs the snippet.** `ProductAnalyticsPanel` (`components/marketing/product-analytics.tsx`) is the one place a site we do not host can be measured, and it shows an install step rather than a zero when nothing has been recorded. The rule is unchanged: a number appears only when a visitor actually reported one. `GrowthOverview` is a discriminated union: `RuntimeGrowthOverview` (metrics, next steps, plan knowledge) or `UnmeasuredGrowthOverview` (`measurementNote`, no metrics, no next steps). `SiteAvailability` gained a separate `external` variant rather than reusing `live`, so an external site is never described as a deployment. `getGrowthOverview({ …, externalSite })` returns the unmeasured variant and **runs no metric query** — a query that returns 0 for a site we do not host is the lie this exists to prevent. `GrowthOverviewView` renders the operate branch (what Atai can see + how to read it) with no page-level heading, because the host page owns the `h1`. Consumers that read metrics or next steps must narrow: `runtimeNextSteps()` for the tasks surfaces, `measurement === "runtime"` for the ads growth centre and the tool projection.
- **Product analytics is one vertical, and both entry points share one normaliser.** `public/atai-analytics.js` (a dependency-free snippet, no cookies, no fingerprint, honours Do Not Track, drops bots) posts to `POST /api/analytics/collect`; server code and the SDK post through the key-authenticated `analytics`/`track`. Both end in `toAnalyticsEvents` (`lib/runtime/router/adapters/analytics/mapper.ts`), which is the only place a path is grouped (`/orders/123` → `/orders/:id`, via `lib/analytics/product/normalize.ts`), a device class is accepted, a click label is bounded and a referrer is reduced to its host. Two normalisers would let the browser and the server count the same page differently, and every read would quietly under-count.
- **A publishable key is the only credential that may live in a page.** `ApiKeyDoc.kind: "publishable"` is issued as `atai_<env>_pk_<secret>`, its scopes are forced to `["analytics"]` at creation whatever the caller asked for, and `POST /api/analytics/collect` refuses any key that is not publishable — a secret key lifted from a server environment must not become a browser credential. The collector stores no IP, no user agent and no cookie (the IP is used for the rate-limit key and discarded), answers `access-control-allow-origin: *`, and treats a bot as `accepted: 0` rather than an error. `"/api/analytics/collect"` is in `PUBLIC_API_PREFIXES` because it must answer a logged-out visitor on a stranger's domain.
- **The read is pure, capped and honest.** `summariseProduct` (`lib/analytics/product/summary.ts`) turns a window of events into sessions, entry/exit pages, bounce rate, top clicks, journeys, devices, referrers and `signals` — and it is pure, so every number on screen is reproducible in a test. `getProductAnalytics` reads newest-first with a 20,000-event cap and marks the result `sampled: true` when the cap is hit; `signals` says nothing below three sessions, and the page-level advice ("this is where people stop") is only offered when a page's exit rate and sample size justify it. Never present a sampled floor as an exact number.
- **A connected business mints its key where it lives.** The operate surface has no project settings page, so `POST /api/businesses/[businessId]/analytics-key` (permission `runtime.keys.manage`, `GET` lists publishable keys only) issues the key and `AnalyticsKeyCard` on `/business/<id>/settings` shows the snippet once. The anchor project id never reaches the browser. The build surface mints the same key at `/project/<id>/runtime/keys` ("Create browser key"); both surfaces read the same `analytics_events` rows and render the same panel.
