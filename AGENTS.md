## Project notes

- Two separate journeys, never merged: **GitHub import** (`/new/github` → `lib/projects/create-project.ts`) brings a repository in to build; **connected business** (`/new/existing` → `lib/existing-business/*`) reads a live website and connects an app that keeps running outside Atai. The existing-business path never reads a repository.
- Onboarding asks the fork before anything else: step 2 of the mission (`/dashboard?mission=1`) is `path` — build something new, bring a codebase, or connect a business that already runs (`ONBOARDING_PATHS` in `lib/onboarding/profile.ts`, rendered by `components/onboarding/path-step.tsx`). `destinationForPath()` in `lib/onboarding/state.ts` decides where it leads: `connect` → `/new/existing`, `import` → `/new/github`, `build` → the vision beat. Never infer the journey from what the founder types; ask.
- The business profile (`/project/[id]/business`) is a three-step stepper — `lib/existing-business/steps.ts` decides order and completion (assessment → domain proof → connection), `components/existing-business/business-profile.tsx` renders only the active step. Keep it one step at a time: a wall of every section at once is what made the page unreadable.
- Connected-business pages share one layout language, matching `/new/existing`: a mono eyebrow (`font-mono text-[11px] uppercase tracking-[0.18em]`), an `h1` at `text-2xl sm:text-3xl`, a `max-w-2xl` support line, then a `lg:grid-cols-[minmax(0,1fr)_300px]` split — the step card on the left, a sticky aside holding the progress rail, a per-step "why this matters", and "what Atai never does". Inside a step card, use numbered sub-steps and `border-t` sections; do not nest `Card` in `Card`.
- A finished step announces itself: `sonner` toast plus a dismissible success strip, and the view advances to the next step. Nothing is marked done on optimism — `businessSteps` reads the same view the server builds.
- Run control is two-phase: `startIntakeRun` awaits only the decision (access, eligibility, rate limit, single-writer claim) so `POST /api/projects/[id]/intake` can answer `started: true|false` or a refusal with a message; `runBusinessIntake` keeps the awaiting form for tests and cron. A fire-and-forget POST cannot tell the founder that a retry was refused, which is exactly how an inert "Try again" button happened.
- After a start the profile polls on its own (`watching`) until the assessment has a verdict — the view returned by a start is the pre-run one, so polling only while `overall` is pending leaves the page frozen on a failed stage.
- Assessment parsing is per-field and tolerant (`normalizeResponse` in `lib/existing-business/assessment.ts`): renamed keys, an omitted section or one weak finding must not fail the whole run. Only a payload with no findings and no priorities is rejected, and a rejected reply gets exactly one repair attempt inside the same charge and time budget. Parse failures are logged with `reason` and `model` — that log line is the answer to "why did the assessment fail?".
- Connection truth lives in `lib/connected-business/` (`businessConnectionStatus` needs both a verified domain and a first authenticated call). Access helpers: `userHasBuiltBusiness` (Atai-built app) vs `userHasRealBusiness` (built **or** connected) in `lib/dashboard/business-access.ts`; nav items declare `requires: "built" | "business"`.
- Connecting a business is priced as a journey, not as whatever pipeline mode the project happens to carry: `existingBusiness.readCost` + `existingBusiness.assessmentCost` in `lib/billing/runtime-config.ts` (admin billing → "Connecting a Business"), charged internally per stage by `chargeBusinessReadCredits` and the assessment's own `consumeCredits` call. `businessJourneyCost()` prices only the stages still unpaid, and both `startIntakeRun` and `GET /api/billing/business-connect` quote it before any work starts.
- Refusals for credits go through `failInsufficientCredits` (402 + `{ required, available, …meta }`) and reach the founder as `CreditsShortfallDialog` — price, balance, exact gap, current step, top-up link — never as a bare red line. Extend the dialog's copy via `describeShortfall` so it stays testable without a DOM (the suite runs in `node`, not jsdom; UI assertions use `renderToStaticMarkup`).
- Phase A2 payment attribution: `lib/billing/subscription-payment-grants.ts` links each subscription payment to the exact ledger grants it funded (`creditsGranted`, `grantLedgerEntryIds`, `grantBucketIds`). `refund.succeeded` reverses only those buckets (`reverseSubscriptionCredits`), never permanent credits or today's catalog; missing or ambiguous grant history stays `reversalStatus: "unresolved"` for review. A grant with only a ledger reference and no `grantBucketIds` is refused (`grant_bucket_unresolved`) rather than guessed. Historical payments reconcile with `scripts/reconcile-subscription-payments.ts` (`dry-run` first, then `apply`); it links only one unambiguous grant and marks everything else `grantStatus: "needs_review"`.
- `reverseCredits` returns `requestedAmount`, `availableAmount`, `expiredAmount`, `consumedAmount`, `previouslyReversedAmount`, `shortfall`, `shortfallReason`, `missingBucketIds`, and the exact `bucketDeductions`. Refunds record that shortfall on both the refund row and the original payment, so "grant was consumed/expired/already reversed" is distinguishable without guessing. The ledger debit and its metadata are written after the flat and bucket updates in the same transaction; a missed bucket write throws and rolls the whole reversal back.
- Phase A4 subscription grants: `grantSubscriptionCredits` reads `subscriptionCredits` and `credits` inside the same transaction that increments them, pushes the bucket and writes the ledger; its ledger snapshot uses the applied `balanceBefore`/`balanceAfter`, plus `totalBalanceBefore`/`totalBalanceAfter`. No balance read or lazy expiry runs before the grant transaction. Duplicate period grants are blocked by the ledger idempotency key and the in-transaction re-check. Renewal expiry passes `expiresAtOrBefore: now` so an annual-sweep bucket for the new period cannot be removed by old-period cleanup; `subscription.expired` still removes the whole subscription. Regression coverage lives in `lib/billing/subscription-payment-grants.test.ts` (Phase A4) and `lib/billing/credit-service.grant.test.ts`.
- Phase A5 infrastructure lifecycle: infrastructure plans are fixed-duration, credit-funded entitlements — there is **no Dodo recurring billing** for them and `autoRenew` stays false. `activatePlan` stores `purchasedTerms` (plan, limits, price, duration), charges the existing ledger with a purchase idempotency key, and applies the Totalum cap; an explicit `{ renewal: true }` extends from the current paid-through date, while an ordinary purchase starts a new period. A short `infrastructure.lifecycleLock` serializes purchase/renewal with `handleExpiration`. `GET /api/admin/infrastructure/expire-sweep` (`0 7 * * *`) downgrades expired paid plans to Testing and applies the real Totalum cap; a cap failure leaves the record `expired` + `syncStatus: "failed"` for retry, and route-level `infrastructureDenial` blocks build/followup/deploy/database/server operations as soon as the paid-through date passes. Historical records with no trustworthy expiry are marked `needsReview`, never auto-expired or repriced. Tests: `lib/infrastructure/lifecycle.test.ts` and the deploy route's expired-infrastructure case.
- Refund concurrency is guarded in three places: the ledger idempotency key, `creditReversalKeys` on the user (one balance decrement per reversal), and `refundIds` on the original payment (one `$inc` per refund). The refund row and the original payment's progress commit in one transaction, and a full refund that lands mid-sweep stops the annual scheduler before the next month.
- Phase A3 credit integrity: `reverseCredits` is the one authoritative reversal path. It debits the exact grant buckets, the flat aggregates and the ledger in a single transaction, and accepts an existing `session`; `reverseSubscriptionCredits` is now a thin wrapper. A grant-scoped reversal (`bucketIds` / `subscriptionId`) never falls back to the customer's total balance, so permanent credits and other subscriptions are untouched. The refund handler runs the reversal, refund row and original-payment progress in that same transaction, and caps cumulative refunds atomically with `refundedAmountMinor: { $lte: originalAmount - refundAmount }` (plus `$exists: false` for the first refund), so two different concurrent refund ids cannot over-refund.
- Cancellation and plan changes never touch credit records: cancellation only changes subscription status, and `subscription.plan_changed` only re-pins terms. Existing buckets keep their original expiry and amounts. Expiry remains scoped to one subscription (`expireSubscriptionCredits`) or to overdue buckets (`expireOverdueBuckets`); promotional grants are permanent credits and are never debited by subscription expiry or refund.
- Legacy bucket/aggregate drift is found by `inspectUserCreditIntegrity` / `auditCreditIntegrity` and repaired by `repairCreditBalance` (`lib/billing/credit-reconciliation.ts`), which aligns `subscriptionCredits`/`credits` to the itemised buckets and writes a `credit_reconciliation` ledger entry with the actor and reason. It never creates or edits a bucket. Run `scripts/reconcile-credit-balances.ts dry-run` first; `apply` requires `--actor` and `--reason`. A legacy account with no buckets is left alone apart from its `credits` mirror.
- **One business belongs to exactly one Atai account.** A business is its live hostname; the claim is the `business_domains` record itself — there is no second registry. `canonicalBusinessHost()` (`lib/domain/host.ts`) strips a safe leading `www.` for the uniqueness key only; the exact hostname stays the verification target, so `www.example.com` and `example.com` are one business, `shop.example.com` is another, and `www.co.uk` is left alone. `canonicalHostname` carries a unique partial index (`business_domains_canonical_active_unique`, excluding released records and `aliasOf` rows) — the database, not a check-then-insert, settles races.
- The claim is taken **before** a project row or a credit: `createUserProject` calls `reserveBusinessClaim` first (reservation only, no token) and reuses the reserved project id. Outcomes: `reserved` → create; `reuse` (same account, another business) → return that project with `reused: true`; `refused` → 409 `BUSINESS_ALREADY_CONNECTED`. Never disclose the holder — `BUSINESS_ALREADY_CONNECTED_MESSAGE` in `lib/domain/claim-copy.ts` (client-safe, imported by the wizard) is the only sentence a founder sees.
- Apex + www inside one project is one business: the second exact host is stored as an `aliasOf` record so it can still be verified. Unverified reservations expire after `CLAIM_RESERVATION_TTL_MS` (72h) — `expireStaleClaims` releases them so the unique index frees up; verified claims never expire. Deleting a project releases every claim in the same transaction (`MongoStore.deleteProject`), and `releaseDomain` refreshes the cached connection status.
- Intake is claim-gated: `ensureBusinessClaim` runs before the credit check and the crawl, and a claim refused at domain registration stops the run before the assessment. The outcome is persisted on `project.intake.claim` (`state: "yours" | "held_by_other"`) and surfaced as `view.claim`; the profile then shows `ClaimHeld` instead of verification controls. Preflight for the wizard is `GET /api/business/availability?url=` (`claimStateFor`) — a failed preflight must never block creation, which re-checks.
- Verify with `npx tsc --noEmit`, `npx vitest run` and `npm run lint` (flat config `eslint.config.mjs`: typescript-eslint recommended + the two classic react-hooks rules + Next's recommended rules; the React Compiler rules in react-hooks v7 are deliberately not enabled). Lint must report zero errors; the remaining warnings are pre-existing `no-explicit-any`/`no-unused-vars` debt.
- A verified claim is evidence that has to keep being true. `lib/domain/recheck.ts` re-checks verified, unreleased domains oldest-first on a daily cron (`GET /api/admin/domains/recheck`, `20 3 * * *`), at most once per `RECHECK_MIN_INTERVAL_MS` (20h), 25 per run with a 240s budget. It calls the same `verifyDomainOwnership({ reverification: true, internal: true })` the founder does — `internal` skips the per-user/per-domain attempt limits, because our own sweep is not a person hammering a check. A failure raises `needsAttention`; only `REVERIFICATION_FAILURE_GRACE` consecutive failures expire the claim, and a sweep never releases a claim on its own.
- The 72h reservation is silent unless we speak: `lib/domain/claim-notices.ts` (`GET /api/admin/domains/claim-notices`, `40 4 * * *`) emails one reminder inside the last 48h of an unverified claim and one notice if it actually expired. The reminder window is deliberately wider than the daily interval so every 72h claim is caught at least once. `expiredUnverified` marks releases that came from the window, so nobody is emailed about a release they performed themselves; `claimReminderSentAt` / `claimExpiryNoticeSentAt` dedupe, and a failed send leaves the flag unset so the next run retries. The deadline is visible in the domain card (`claimExpiresAt` on `DomainView`, `relativeDeadline()` in `lib/client/format.ts`).
- Support release is the audited exception, not a code change: `lib/domain/claims-admin.ts` backs both `/admin/domains/claims` and `scripts/release-business-claim.ts`, and both write `released by support (<actor>): <reason>` into the record's history. A reason is mandatory. It never deletes anything — the record is marked `revoked` + `releasedAt`, so the unique index frees the hostname and the audit trail survives.
- The verification token is encrypted at rest (`lib/domain/token-cipher.ts`, AES-256-GCM, key derived from `AUTH_SECRET` or an explicit 32-byte `DOMAIN_TOKEN_KEY`). Storage holds ciphertext; service callers work with plaintext — `getOwnedDomain` / `listProjectDomains` / `toDomainView` decrypt, `registerDomain` / `ensureChallenge` / `regenerateChallenge` encrypt on write. `decryptDomainToken` passes through legacy plaintext values, so old rows keep working until they expire or are regenerated. Never log or return `token` outside the owner-gated view.
- The connect journey is instrumented separately from the build funnel: `lib/analytics/connect-funnel.ts` emits `connect_started` → `connect_submitted` → `connect_read_completed` → `connect_verified` → `connect_completed`, plus `connect_claim_blocked` (with `state: held_by_other | held_by_same_account`) which is the signal that separates a blocked squatter from a blocked real owner. Flat primitives only; never send the hostname, URL, project id or email — a random `flow_id` joins the steps.
- Root of the repo is source and config only: `README.md`, `CHANGELOG.md`, `AGENTS.md`, `CLAUDE.md`, configs. Implementation reports go in `docs/history/`, audits in `docs/audits/`; build artifacts (`*.tsbuildinfo`, `tsc-*.txt`, `test-out.txt`, probe scripts) are ignored and must not be committed.
- `pnpm` is the only package manager (`packageManager: pnpm@10.6.0`, `pnpm-lock.yaml`). Do not reintroduce `package-lock.json` — two lockfiles can disagree and CI installs with `pnpm install --frozen-lockfile`. CI (`.github/workflows/ci.yml`) runs typecheck → lint → tests → build, so lint warnings that become errors block a merge.
- Plan enforcement is centralized in `lib/billing/entitlements/require.ts`: a production build/follow-up checks `buildProduction` + `provisionDatabase` + `useSpecialistTeam` in one fresh decision, deploy checks `connectSubdomain` only when the project has no published URL, and custom domains spend a registration only when none exists. Existing domains/subdomains stay manageable after a downgrade.
- `GET /api/projects/[id]` returns `access` (`ProjectAccessView` from `lib/billing/entitlements/presentation.ts`) so the UI can disable actions and show the server's reason. It is presentation only; every mutating route re-checks. Terminated paid subscriptions fall back to Explorer; only a legacy free account that never subscribed keeps grandfathered production capability.
- Capacity is reserved, not just read: `lib/billing/entitlements/reservations.ts` serializes the read-check-reserve section with a short DB lock and writes a TTL hold (`billing_resource_holds`) before the provider runs. Custom-domain/subdomain holds count toward the cap; storage holds count bytes until the asset row exists. Routes call `reserveCustomDomainSlot` / `reserveSubdomainSlot` / `reserveProjectStorage` instead of authorize-then-write — two requests can otherwise both see the last slot. Provider failure releases the hold; a provider success followed by a failed project write keeps it so a retry cannot hand the slot to another request. Expired holds are never counted and TTL indexes clean them up. Both the REST deploy route and the shared `startProjectDeploy` (Co-founder tool + pipeline recovery) use the same sequence, and `state: "deploying"` counts as a subdomain slot. `ENTITLEMENT_ENFORCEMENT_ENABLED=false` fails plan-capability guards and the access view open, but keeps the pre-existing infrastructure storage byte quota, credit checks and provider checks running — it disables the entitlement layer, not every guard.
- An uninitialized project has no free pass: `getProjectStorageUsage` falls back to the Testing 50MB cap when no infrastructure record exists, so uploads before the first build cannot bypass the quota. `lib/billing/entitlements/hold-maintenance.ts` and the daily `GET|POST /api/admin/billing/entitlements/resource-holds` sweep (`50 3 * * *`) delete expired locks/holds, release holds for deleted projects or already-persisted domains/subdomains, and leave live storage holds until TTL. Use `?dryRun=true` before manual cleanup.
- `next.config.mjs` sets the security headers (`X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, COOP, HSTS) and a **report-only** CSP — report-only on purpose, because App Router ships inline bootstrap scripts and an enforced `script-src` needs nonces through middleware. `images.unoptimized` is deliberate (ImageKit already optimizes; Vercel's optimizer would bill a second pass).
